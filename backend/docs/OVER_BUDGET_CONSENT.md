# 예산 초과 확인 (로컬 확장 — 팀 합의 전)

예산 안에 드는 가게가 없어서 A가 "가장 가까운" 후보(`violations: BUDGET_EXCEEDED`)를 돌려줄 때,
사용자가 그 사실을 알고도 계속하겠다고 하면 **그 주문에 한해** 진행한다.
명세에 없는 **선택 필드**만 더했고, 필드를 안 보내면 기존 동작과 같다(D-02가 BUDGET_EXCEEDED로 막는다).

## 사용자 흐름 (화면 03 후보 선택)

| 상황 | 화면 | 사용자 | 결과 |
| --- | --- | --- | --- |
| 모든 후보가 예산 초과 | 팝업: "지정 금액에 해당하는 메뉴와 가게가 없어서 예산 초과의 가게를 추천합니다. 계속 주문하시겠습니까?" | **예** | 후보를 고르면 동의가 함께 전달되고 결제까지 진행 |
| | | **아니오** | O-02 CANCEL 후 처음 화면(`/`)으로 |
| 예산 안 후보도 있는데 예산 초과 후보를 고름 | 팝업: "선택한 가게는 예산을 넘어요. 계속 주문하시겠습니까?" | **예** | 그 후보로 진행 |
| | | **아니오** | 팝업만 닫고 후보 목록에 머문다 |
| 승인(05) | 예산을 넘는 주문이면 배너와 확인 항목 표시 | | "예산 N원보다 M원 많음 (사용자 확인)" |

## API 변경

| 위치 | 필드 | 설명 |
| --- | --- | --- |
| O-02 `SELECT_CANDIDATE` 요청 | `allow_over_budget` (bool, 선택, 기본 false) | 사용자가 예산 초과를 알고 계속하겠다고 답했는가 |
| O-02/O-03 `APPROVAL` prompt | `over_budget {limit_krw, charge_krw, over_krw}` (있을 때만) | 예산을 넘겨 진행하는 주문의 한도·결제금액·초과분 |
| `APPROVAL.checks` | "예산 N원보다 M원 많음 (사용자 확인)" | 예산 초과일 때 "예산 N원 이내" 대신 표시 |

A·B·C·D·E의 API는 바꾸지 않았다. D는 기존 D-01 재등록(조건·위임 재등록)을 그대로 쓴다.

## 동작 규칙 (O)

D의 검사 규칙은 그대로이고, 아래 조건을 **모두** 만족할 때만 O가 이 주문의 한도를 올린다. 하나라도 어긋나면 D가 평소처럼 막는다.

1. `allow_over_budget=true`이고, 선택한 후보를 A가 `BUDGET_EXCEEDED`로 표시했다 (동의는 후보를 고를 때마다 새로 정함).
2. 결제수단 선택 뒤 B 견적의 최종 결제금액(`charge_krw`)이 후보 화면에서 사용자가 본 금액(`estimated_total_krw`) 이하다.
3. 그때 O가 D-01을 다시 등록한다: `constraints.budget_krw`와 `delegation.max_charge_krw`(둘 중 값이 있는 것)를 이번 결제금액까지 올림 → D-02가 새 정책 버전으로 검증.

- 사용자의 원래 위임 설정(`run.delegation`)과 A의 조건은 바꾸지 않는다 (이 주문의 D 정책에만 반영).
- 동의는 O-04 기록(`USER_REPLY`의 `allow_over_budget`)과 D-01 재등록 호출(`SERVICE_CALL`)로 남는다.
- 최종 승인(05)에서 사용자가 정확한 금액을 한 번 더 확인하고 승인한다.

## 팀 합의 때 확인할 점

- `allow_over_budget`을 O-02 명세에 정식 필드로 넣을지 (지금은 선택 필드).
- 예산을 넘는 주문을 D가 직접 알도록 할지 (지금은 O가 D-01 재등록으로 한도를 올림. D에 "사용자 확인한 초과 허용" 필드를 두는 방식도 가능).
- 초과 허용 범위: 지금은 "사용자가 본 후보 금액 이하"로만 제한. 별도 상한(예: 예산의 N배)을 둘지.
- 위임 상한(`max_charge_krw`)만 걸려 있고 문장에 예산이 없어 A가 초과로 표시하지 않는 경우는 이 흐름에 포함되지 않는다 (기존처럼 D가 차단).
