# 최소주문금액 미달 후보 막기 (로컬 확장, API 명세 밖)

후보 목록에서 **최소주문금액이 맞지 않아 주문할 수 없는 가게**를 미리 알려 주고, 선택하지 못하게 한다.

## 왜 필요한가

13,000원 주문(예: 배떡-충무로점 국물떡볶이 2개 + 배달비)이 후보로 나왔는데, 결제수단까지 고르고
최종 주문을 하면 "맡긴 조건을 벗어나서 결제하지 않았어요"(BLOCKED)가 나왔다.

- 가게 최소주문금액(12,000원)은 채웠다. A·B가 이미 확인한다.
- 막은 쪽은 **결제수단 혜택 규칙의 최소주문금액**이다 (가상카드 A: 15,000원 이상).
  C-05가 `eligible=false`(MIN_ORDER_NOT_MET)로 답하고, B-05가 `409 PAYMENT_METHOD_NOT_ELIGIBLE`로
  거절해서 O가 BLOCKED로 멈췄다.
- 그런데 C-01 추천은 이런 수단을 "혜택 없음"으로 선택지에 남겨 둬서, 화면에서는 골라지는데 뒤에서 막혔다.

## 동작

1. O가 후보를 만들 때(A-05 직후) C에 `check_min_order`를 한 번 부른다. 읽기 전용이라 C-01 추천 기록을 남기지 않는다.
2. 맡긴 결제수단을 **하나도 쓸 수 없고**, 최소주문금액만 채우면 쓸 수 있는 수단이 있으면 그 후보는 주문 불가다.
   (쓸 수 있는 수단이 하나라도 있거나, 실적·가맹점 같은 다른 사유로 못 쓰면 표시하지 않는다.)
3. O-02 후보 프롬프트(`SELECT_CANDIDATE.candidates[]`)에 필드가 더해진다.

| 필드 | 값 |
|---|---|
| `orderable` | 주문 불가면 `false`, 아니면 `true` |
| `min_order` | `{required_krw, order_krw}` (필요한 최소주문금액, 현재 주문 금액). 주문 가능이면 `null` |
| `violations` | 주문 불가면 `{code: "MIN_ORDER_NOT_MET", message: "최소주문금액이 맞지 않아서 주문이 불가합니다"}`가 더해진다 |
| `meets_all_constraints` | 주문 불가면 `false` |

4. 주문 불가 후보로 `SELECT_CANDIDATE`를 보내면 `400 VALIDATION_ERROR` (`fields[0].reason = "min_order_not_met"`).
5. 화면(`Candidates.tsx`): 주문 불가 카드는 회색 비활성이고 눌러도 선택되지 않는다. 카드 아래에
   "최소주문금액이 맞지 않아서 주문이 불가합니다"와 필요 금액·현재 금액을 보여 준다.
   주문 가능한 후보가 하나도 없으면 안내와 함께 "조건 바꿔 다시 주문" 버튼만 보인다.

## 안전장치

- 확인하지 못하면(C가 이 확인을 모르거나 장애) 아무것도 표시하지 않고 기존 흐름대로 간다. B-05가 마지막 방어선이다.
- 로컬 확장이라 O→C 호출이 하나 늘었다: `benefit.facade.check_min_order` (`_RealBenefit`에 연결).

## 참고: 남은 불일치

C-01은 `MIN_ORDER_NOT_MET`·`RULE_NOT_FOUND`·`BENEFIT_LIMIT_EXCEEDED`인 수단을 "혜택 없음" 선택지로 남기지만,
B-05는 `eligible=false`를 거절한다. 이번 변경은 금액 미달만 후보 단계에서 막는다.
나머지 두 경우와 C-01의 선택지 정책은 팀 협의가 필요하다.
