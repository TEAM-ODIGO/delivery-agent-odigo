# A 서비스 · 탐색·추천 (discovery)

자연어 배달 주문 AI Agent의 A 모듈입니다. FastAPI + PostgreSQL, 조건 추출은 Ollama 로컬 LLM을 쓰고 실패하면 규칙 기반으로 대체합니다.

## 구현 범위 (0순위 = MVP 1)

| ID | 경로 | 내용 |
|---|---|---|
| A-01 | `POST /discovery/requests` | 자연어 → 조건 추출, 부족하면 `NEED_CLARIFICATION` + 선택·입력 질문 |
| A-02 | `GET /discovery/requests/{request_id}` | 요청 상태·조건·현재 후보 조회 |
| A-04 | `PATCH /discovery/requests/{request_id}/constraints` | 부족 조건 입력·조건 직접 수정 (MVP 1 재질문) |
| A-05 | `POST /discovery/requests/{request_id}/search` | 음식점·메뉴 탐색, 점수순 후보 + 조건 완화 제안 |
| A-06 | `POST /discovery/requests/{request_id}/select` | 후보 선택 기록 |
| (A-10) | `GET /discovery/health` | 상태 확인 (DB + LLM 연결) |

1순위(A-03·07·08·09 REST)는 만들지 않았습니다. A-09 LLM 라우팅은 명세 제안대로 내부 함수(`app/discovery/llm.py`)로 두었고, A-08용 LLM 호출 기록(`a_llm_call`)과 조건 이력(`a_constraints_history`)은 MVP 1부터 남깁니다.

## 폴더 구조

```
app/
  main.py                 A 모듈만 단독 실행할 때의 진입점
  common/                 팀 공통으로 옮겨도 되는 부분
    config.py             .env 설정
    db.py                 SQLAlchemy 엔진·세션, KST 시간
    errors.py             AppError + 공통 에러 JSON {"error": {...}, "request_id"}
    security.py           서비스 토큰 확인
    yogiyo_models.py      공용 읽기 전용 테이블 restaurant·menu
  discovery/
    router.py             HTTP 엔드포인트 (얇게, 검증만)
    service.py            업무 로직 (O가 함수로 바로 호출하는 곳)
    extractor.py          규칙 기반 조건 추출
    llm.py                Ollama 호출 + 실패 시 None
    search.py             필터·장바구니·점수·완화 제안
    constants.py          상태 이름, 필수 조건, 음식 종류 사전
    models.py             a_request·a_constraints_history·a_candidate·a_llm_call
    schemas.py            요청·응답 pydantic 모델
scripts/load_yogiyo.py    요기요 CSV → PostgreSQL 적재
tests/                    pytest (가짜 가게 4곳으로 시나리오 검증)
data/                     크롤링 CSV (을지로입구역 기준 식당 158곳, 메뉴 9,460개)
```

## 실행

```bash
python3.14 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env            # DATABASE_URL, INTERNAL_SERVICE_TOKEN 수정

createdb delivery               # PostgreSQL 18
python -m scripts.load_yogiyo --restaurants data/1_식당.csv --menus data/2_메뉴.csv

uvicorn app.main:app --reload --port 8000
# http://localhost:8000/docs → 오른쪽 위 Authorize에 .env의 INTERNAL_SERVICE_TOKEN 값 입력 (Bearer 없이 토큰만)
```

LLM을 쓰려면 Ollama를 설치하고 `ollama pull qwen2.5:7b` 후 `ollama serve`. 꺼져 있어도 규칙 기반으로 동작하고, `/discovery/health`의 `llm` 값으로 상태를 볼 수 있습니다(`UP`·`DOWN`·`MODEL_MISSING`·`DISABLED`).

## O(오케스트레이터)에서 쓰는 법

같은 서버 안의 모듈이라 HTTP 대신 함수로 부르면 됩니다. 실패는 `AppError(status_code, code, message, details)`로 올라옵니다.

```python
from app.discovery import service as discovery
from app.discovery.schemas import CreateRequestBody, ConstraintsPatch

result = discovery.create_request(db, CreateRequestBody(request_id=rid, user_id=uid, message=msg, delivery_address=addr))
if result["status"] == "CONFIRMED":
    ...  # D-01 등록 → discovery.search_request(db, rid, top_n=3)
```

팀 main.py에 합칠 때는 `app.include_router(discovery_router)`와 `register_error_handlers(app)`만 넣으면 됩니다.

## 추천 방식 (A-05)

1. 가게 거르기: 음식 종류(요기요 카테고리), '지역화폐만'이면 `local_currency_merchant = true`만
2. 메뉴 거르기: 품절·주류·음료·사이드 제외, 제외 재료가 이름·설명에 있으면 제외, 맵기 상한 초과 제외(맵기 정보가 없으면 '매운·마라·짬뽕' 같은 이름으로 한 번 더 거름), 가게 중간 가격의 40% 미만인 '메인'(김말이·할인 쿠폰성 메뉴)은 제외
3. 장바구니: 인원수를 채우는 메뉴 1종 또는 2종 조합을 만들고 최소주문금액·주문금액별 배달비 반영. 사용자가 말한 메뉴(예: 짜장)가 들어간 조합을 우선
4. 점수(100점): 보정별점 30 · 리뷰 수 10 · 배달 속도 15 · 가격 15 · 메뉴 인기 10 · 주력 음식 10 · 요청 메뉴 10, 조건 위반마다 −20
   (맛을 말했으면 '주력 음식 10'은 가게 메뉴 중 그 맛 메뉴 비율로 계산. 음식 종류도 말했으면 5점씩)
5. 같은 브랜드는 1곳만, 모두 만족하는 후보가 없으면 가장 가까운 후보를 `violations`와 함께 반환
6. 후보가 모자라면 `relaxation_suggestions`로 "예산을 23,000원으로 올리면 2곳 더" 같은 제안

## 맛으로 찾기 (taste_preferences, 2026-11-17 추가)

"매운 음식", "달달한 거"처럼 메뉴 이름 없이 맛만 말해도 그 맛을 주로 파는 가게와 메뉴를 추천합니다.
LLM 없이 규칙만으로 동작합니다. 맛 단어 목록은 수집 메뉴 이름을 세어 보고 정했습니다(`constants.TASTES`).

| 코드 | 이런 말을 하면 | 메뉴 판단 (데이터 값이 있으면 데이터 우선) |
|---|---|---|
| `SPICY` 매운 | 매운, 매콤, 칼칼, 얼큰, 화끈 | 이름에 매운·마라·얼큰 등이 있으면 O, 로제·순한·사골·순대국밥 등이 있으면 X, 그 외 맵기 2·3단계, 맵기 정보가 없으면 이름(떡볶이·닭발·짬뽕…) |
| `SWEET` 달달한 | 달달, 달콤, 단 거, 디저트, 후식 | 이름(허니·꿀·고구마·초코·크로플…). '꿀조합'·음료는 제외 |
| `SOUP` 국물 | 국물, 뜨끈한, 해장, 시원한 국 | 냉면·물회 같은 찬 국물과 김밥·마제소바·볶음·비빔은 X, 그 외 국물 있음 데이터, 데이터가 없으면 이름(국밥·찌개·만두국…) |
| `CRISPY` 바삭한 | 바삭, 튀긴, 튀김, 겉바 | 이름(후라이드·튀김·돈까스·강정…) |
| `LIGHT` 담백한 | 담백, 가벼운, 건강한, 속 편한 | 이름(샐러드·포케·죽·초밥…). 맵기 2 이상·튀김·크림류는 제외 |
| `CHEESY` 고소·꾸덕 | 꾸덕, 고소한, 느끼한, 크리미 | 이름(치즈·크림·로제·까르보…) |

- '느끼한 건 싫어', '단 거 말고'처럼 부정하면 넣지 않습니다. '매운 거 말고'는 `max_spice_level: 0`이 됩니다.
- '안 매운'·'덜 매운'은 예전처럼 맵기 상한(`max_spice_level` 0·1)이고, '매운'은 상한이 아니라 `SPICY`입니다.
- 이름 규칙을 수집 데이터보다 앞에 둔 이유: 데이터에 순대국밥 맵기 3·얼큰떡만두국 맵기 2처럼 거꾸로 된 값, 천국김밥·마제소바가 '국물 있음'인 값이 있었습니다.
- 맛을 여러 개 말하면(얼큰한 국물 → `SPICY`+`SOUP`) 모두 만족하는 메뉴를 찾습니다.
- 그 맛 메뉴가 20% 이상인 가게를 먼저 보여 주고, 모자라면 그 맛 메뉴가 있는 다른 가게로 채웁니다.
- 그 맛 메뉴가 하나도 없으면 비슷한 가게를 보여 주고 `relaxation_suggestions`에 `taste_preferences`를 넣습니다.
- 한계: 크롤링 범위(피자·분식·일식·한식·치킨·중식)에 디저트 가게가 없어 '달달한 거'만 말하면 쿠키·크로플 같은 간식이 주로 나옵니다. '달달한 치킨'처럼 음식 종류와 같이 말하면 허니·양념치킨이 나옵니다.

## 규칙 결과와 LLM 결과 합치기 (2026-11-17 변경)

예전에는 LLM 값을 먼저 썼는데, 로컬 LLM(qwen2.5 7B)이 '혼자 만오천원 국물 있는 거'를
예산 5,000원·음식 종류 분식·메뉴 '국물'로 읽어 엉뚱한 추천이 나왔습니다. 그래서 순서를 바꿨습니다.

- **숫자 조건**(예산·인원·배달 시간·맵기 상한): 규칙이 문장에서 찾은 값이 있으면 규칙 값. 규칙이 못 찾았을 때만, 문장에 근거 단어(원·만·명·분·맵…)가 있으면 LLM 값.
- **범위를 좁히는 조건**(음식 종류·메뉴·제외 재료·맛·지역화폐만): 문장에 그 단어가 실제로 있을 때만 LLM 값을 더함. '국물'·'음식' 같은 일반 단어와 맛 단어는 메뉴 검색어로 쓰지 않음.
- 근거 단어 목록: `extractor.LLM_HINTS`, `TASTE_HINTS`, `GENERIC_MENU_WORDS`

## 팀과 맞춰야 할 것 (제가 정한 가정)

1. **필수 조건은 `people`·`budget_krw`** 두 개만. 음식 종류가 없으면 전체에서 찾습니다. (`constants.REQUIRED_SLOTS`)
2. **예산에는 배달비가 포함**됩니다(`estimated_total_krw` = 메뉴 합계 + 배달비).
3. **배달 시간은 요기요 '23~38분' 중 늦은 값(38분)**으로 판정합니다. 그래서 '30분 안에'는 대부분 위반이 나옵니다.
4. **배송지로 거리를 다시 계산하지 않습니다.** 수집 데이터가 을지로입구역 기준이고 가게 좌표가 없어서, `delivery_address`는 조건에 그대로 저장만 합니다.
5. **옵션 데이터가 없어 `option_ids`는 빈 목록**이고 `unit_price_krw`는 필수옵션 포함가입니다. 필수 옵션 선택은 B에서 처리가 필요합니다.
6. `violations` 형태는 `{"code", "message", "limit", "actual"}` (코드: `BUDGET_EXCEEDED`, `DELIVERY_TIME_EXCEEDED`)로 정했습니다. 명세 예시는 빈 배열뿐이라 D와 맞춰야 합니다.
7. 명세에 없던 값 몇 가지를 더했습니다: A-05 응답의 `constraints_version`, 추천할 가게가 없을 때 응답 `status: "NO_CANDIDATES"`(요청 상태는 `CONFIRMED` 유지), A-01 같은 `request_id`로 다른 내용을 보내면 `409 IDEMPOTENCY_CONFLICT`.
8. 제외 재료는 재료표가 없어 메뉴 이름·설명 글자로만 판단합니다. 추천 근거에도 그렇게 적습니다.
9. 요청 값 오류는 공통 규칙대로 `400 VALIDATION_ERROR`로 통일했습니다(FastAPI 기본 422 대신).
10. **조건에 `taste_preferences`(맛 취향 코드 목록)를 더했습니다.** 명세의 constraints에 없는 A 확장이라 D·B에는 공유가 필요합니다. D가 모르는 필드를 거부하면 통합할 때 D에도 추가해야 합니다.
